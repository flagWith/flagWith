## 한 줄 요약

**flagWith**는 CTF 주최측이 대회 참가팀들에게 제공하는, GitHub 방식의 팀 전용 작업공간이다. 각 팀은 자신의 워크스페이스에서만 협업하고, 대회가 끝나면 자동으로 잠겨서 그동안의 작업 기록이 라이트업 쓸 때 참고할 타임라인 페이지로 남는다. 주최측은 대회 진행 중 참가팀들의 풀이 진행 현황과 활동 로그를 실시간으로 들여다볼 수 있다. *(코드·메모 내용은 팀 비밀번호로 암호화되어 주최측도 볼 수 없다)*

## 왜 이걸 만드나

CTF(Capture The Flag)는 해킹 실력을 겨루는 문제풀이형 대회다. 문제 파일은 각자 다운로드해서 개별적으로 푸는 형태가 기본이지만, 실제 대회는 대부분 팀 단위로 진행된다. 그런데 팀으로 뛰다 보면 한 사람이 발견한 아이디어나 접근 방식을 말로만 설명해서는 팀원 전체가 그 내용을 다 기억하기 어렵다. 같은 문제를 다같이 들여다보며 생각을 주고받는 것이 풀이의 핵심인데, 정작 그 "같이 보는" 과정 자체가 매끄럽지 않은 것이다.

팀원끼리 물리적으로 멀리 떨어져 온라인으로 진행되는 대회에선 이 문제가 훨씬 크게 느껴졌다. 코드 하나를 공유하려 해도 개별적으로 파일을 전송하거나, 디스코드 같은 외부 앱을 따로 열어 파일을 주고받아야 했다. 그 과정에서 흐름이 자꾸 끊기고 몰입감이 깨졌다.

그래서 떠올린 게 GitHub 같은 웹 기반 공동 작업 공간이었다. 팀원 모두가 같은 코드를 동시에 보면서 토론하고, 메모를 남기고, 코드를 일부 수정·패치하면서 진행 상황을 한 화면에서 실시간으로 공유할 수 있다면 어떨까. '브랜치' 같은 기능을 쓰면 원본은 그대로 둔 채 각자 다른 접근을 실험해보고, 잘 되면 다시 합칠 수도 있다.

무엇보다 핵심은 라이트업 작성이었다. 혼자 푼 문제는 어느 정도 정리가 되지만, 팀이 같이 매달린 문제는 얘기가 다르다. 내가 다른 문제를 붙잡고 있는 동안 다른 팀원이 어떤 생각으로 어떤 시도를 했는지, 그 흐름을 나중에 모아서 글로 정리하는 건 훨씬 어렵다. 작업 과정을 어딘가에 자동으로 기록해두고, 그걸 바탕으로 풀이 타임라인을 제공할 수 있다면 라이트업을 쓸 때도 큰 도움이 될 거라 판단했다.

git과 GitHub이 등장한 뒤로 개발 협업의 방식 자체가 바뀐 것처럼, 이 아이디어도 CTF를 준비하고 참여하는 방식에 비슷한 수준의 변화를 가져올 수 있다고 본다.

## 기획 과정 — 두 가지 문제와 재정의

기획 초기에 두 가지 지적이 나왔다.

1. 비슷한 도구(**CTFNote**)가 이미 있다.
2. 더 결정적으로: 팀의 풀이·익스플로잇 코드가 저장소에 남으면, 같은 문제(또는 변형)를 재사용하는 다른 대회에서 답이 그대로 새어나갈 수 있다는 지적.

### 재정의: "참가자한테 새는 건 원래 당연하다. 막아야 할 건 그 다음이다"

문제 파일을 받아서 푸는 이상, 참가자가 그 파일을 갖고 있는 것 자체는 막을 수 없다. 진짜 막아야 하는 건 그 결과물이 **제3자가 접근할 수 있거나, 서버가 뚫렸을 때 데이터가 새는 것**이다. 이 재정의 하나로 원래 아이디어가 다시 성립하게 됐다.

### 피드백 반영: 타겟층을 참가자에서 주최측으로

처음에는 참가자(팀) 대상으로 기획된 아이디어였다. 여기서 제3자·서버 탈취에 의한 데이터 유출 방어책은 생각해봤지만, 정작 주최측에서 가장 걱정하는 지점 — **타팀 간 협업 및 풀이 공유** — 을 막을 방법은 생각해내지 못했다.

여기서 발상을 뒤집어, 타겟층 자체를 참가자가 아니라 **CTF 주최측**으로 잡았다. 이 경우 다음과 같은 이점이 있다.

1. **타팀 협업 문제 해결** — 주최측이 팀원들끼리 레포를 구성시키고 자신의 레포에만 접근을 제한해두면, 타팀 간 협업/공유 문제를 막을 수 있다.
2. **주최측에 새로운 인사이트 제공** — 주최측이 참가자들의 풀이 진행 상황을 실시간으로 지켜볼 수 있다. 라이트업으로는 느낄 수 없었던 참가자 인사이트와 풀이 과정을(코드 내용이 아닌 진행 현황·활동 로그로) 지켜볼 수 있다.
3. **차별화** — 기존 사이트 "CTFNote"는 참가자 대상이었다. 주최측을 타겟으로 잡은 프로젝트는 조사한 바로는 없어 신선한 아이디어라 판단된다.

> 이 피봇에 따라 "누가 계정을 만들고 누가 비용을 지불하는가"가 참가자 개인에서 대회 운영진(조직)으로 바뀐다. 온보딩 방식은 **상시 서비스형(SaaS)**으로 결정했다.

### 주최측 온보딩 방식 — 상시 서비스형 (모델 B)

대회당 직접 세팅해주는 1회성 배포가 아니라, **주최측이 직접 가입해서 스스로 대회를 만들고 운영하는 SaaS 형태**로 간다. GitHub처럼 하나의 계정으로 여러 대회를 계속 만들고 운영할 수 있는 구조다.

- 주최측은 회원가입 후 로그인해서 스스로 대회를 만들고, 참가팀·팀원을 등록하면 팀 이름을 딴 워크스페이스가 함께 생성된다.
- 매 대회마다 수동 개입 불필요 — 온보딩부터 종료까지 셀프서비스.
- 계정/로그인 시스템(회원가입, 마이페이지 등)이 MVP 범위에 정식 포함.
- 계정에는 호스트/참가자 역할 구분이 없다. CTF를 만든 계정이 그 CTF의 호스트, 팀에 등록된 계정이 그 CTF의 참가자가 된다. 계정당 만들 수 있는 CTF는 종료된 것 포함 최대 3개.
- 로그인 식별자는 이메일이다. 가입 시 이메일 인증은 하지 않으므로(알려진 한계) 호스트가 이메일로 팀원을 등록할 때는 본인 확인이 필요하다. 비밀번호 찾기는 이메일로 받은 재설정 링크(5분 유효)로 한다.
- 팀장은 호스트가 팀을 등록할 때 함께 지정하며, 바꾸는 기능은 없다.
- 지원하는 대회 형식은 Jeopardy뿐이다.

> 과금/요금제 방식(대회당 과금 vs 구독제 등)은 아직 미정 — [아직 안 정한 것](#아직-안-정한-것) 참고.

## 핵심 기능

### 1. 팀·대회 단위로 격리된 워크스페이스

주최측이 팀/유저를 등록하면 팀별로 워크스페이스가(팀 이름으로) 함께 생성되고, 각 팀은 자신의 레포에만 접근 가능하도록 강제하는 git 기반 작업공간. 이 격리 자체가 타팀 간 협업/풀이 공유를 막는 핵심 장치다. git 엔진은 기존 오픈소스에 얹지 않고 **직접 구현**한다. 플랫폼은 MVP 기준 **웹 전용**이며, 표준 git(터미널) 워크플로우 지원은 **v2 로드맵**으로 미룬다.

**사이드바 구조**는 VSC 사이드바처럼 폴더·파일 트리로 구성되며, 위에서 아래로 3개 영역으로 나뉜다.

- **문제 파일 부**: 대회 문제파일(챌린지 자료) — 참가자 전원 공통, 읽기 전용 (`problem_files` 영역)
- **유저 파일 부**: 팀이 직접 만들고 커밋하는 git 작업 파일. 문제마다 팀 풀이 영역(`team_work`)과 라이트업 영역(`writeup`)으로 나뉜다.
- **브랜치 부**: 브랜치 탭 — 브랜치 생성·삭제·병합·전환

**파일 모델 — 폴더 없음 (GitHub 방식)**

- 폴더를 따로 저장하지 않는다. 저장하는 것은 파일뿐이고, 파일 경로(`file_path`)에 `/`가 들어 있으면 화면이 그 부분을 폴더로 렌더링한다. (예: `exploit/solve.py` → `exploit` 폴더 안의 `solve.py`)
- 위 영역(문제 파일 / 팀 풀이 / 라이트업)도 폴더가 아니라 파일의 `area` 값이다. 파일의 위치는 (워크스페이스, 브랜치, 문제, 영역, `file_path`)로 정해진다.
- 폴더는 그 아래에 파일이 하나라도 있을 때만 보이고, 마지막 파일이 삭제·이동되면 자동으로 사라진다. 빈 폴더는 만들 수 없고 폴더 단위 생성·삭제·이름 변경 기능도 없다.
- `file_path` 규칙: `/`로 계층을 구분하고, 앞뒤 `/`·연속 `//`·빈 세그먼트·`.`/`..` 세그먼트·제어 문자는 허용하지 않는다. 길이는 세그먼트당 255자, 전체 1024자 이내. 같은 위치 안에서 경로는 유일하며, 어떤 파일의 경로가 다른 파일의 폴더 경로와 겹칠 수 없다. (`a` 파일과 `a/b` 파일은 공존 불가)
- 문제 파일 영역은 호스트가 등록한 원본 그대로 보존된다(생성·수정·삭제·이동 금지). 어떤 파일이든 복사할 수 있지만 문제 파일 영역에는 복사본을 만들 수 없다. 원본을 고치려면 팀 풀이 영역에 복사해서 작업한다.
- 파일 경로(파일 이름·폴더 구조)는 암호화하지 않는다. 암호화하는 것은 파일 내용과 메모다.

**동의 기반 수정 (웹소켓 실시간)**

- 파일 수정·파일 삭제·브랜치 삭제는 바로 반영되지 않고 동의를 거친다. 승인자는 요청 시점에 그 파일(브랜치 삭제는 그 브랜치)을 열어둔 다른 팀원 전원이며, 보기만 하는 팀원도 포함한다. 열어둔 팀원이 없으면 즉시 반영된다. 동의 요청에는 요청자·수정 메시지·수정된 내용이 함께 전달된다.
- 전원 동의하면 반영된다. 반대가 나오면 자동 반영되지 않고 팀장이 강제 적용할 수 있으며, 요청 후 60초 안에 처리되지 않으면 취소된다. 60초 안에 응답하지 않은 승인자는 반대로 처리한다.
- 대기 중에 같은 대상에 다른 수정이 먼저 반영되면 요청은 자동 무효가 된다(자동 병합 없음). 같은 파일(브랜치)에 대기 중인 요청은 1개만 허용한다.
- 브랜치 병합은 열어둔 팀원의 동의가 아니라 팀장 한 명의 동의만 필요하다(팀장이 직접 요청하면 즉시 병합, 응답 시한 없음).
- 파일 생성·이동·복사·메모와 풀이 완료 표시는 동의 없이 즉시 반영된다.
- 알림과 응답은 폴링이 아니라 웹소켓으로 실시간 처리한다. 열람 상태도 웹소켓 연결로 기록하며, 연결이 끊기면 10초 뒤, 탭이 5분 이상 비활성이면 열람 중에서 빠진다.
- 웹소켓 보안: 연결할 때뿐 아니라 메시지마다 팀 소속과 잠금 여부를 다시 확인하고, Origin을 검사하며, 마스터 키는 소켓으로 보내지 않는다. 대회 종료 시 해당 CTF의 연결을 모두 끊는다.

### 2. 대회 종료 시 자동 잠금

대회가 끝나는 순간 파일 생성·수정·삭제·이동·복사·메모, 브랜치 작업, 풀이 완료 표시 같은 모든 쓰기가 막힌다. 더 이상 아무도 수정할 수 없는 "스냅샷" 상태가 되며, 읽기 전용 열람만 가능하다.

- 종료 시각이 지난 워크스페이스는 스케줄러(10분 간격)가 잠금 상태로 바꾸고, 그 사이의 공백은 쓰기 요청마다 종료 여부를 검사해 막는다.
- 잠금과 함께 해당 CTF 워크스페이스의 마스터 키 캐시를 폐기하고, 대기 중인 수정·병합 요청을 취소하고, 실시간 연결을 끊는다. (로그인 세션은 유지 — 이후 읽기 전용 열람은 워크스페이스 비밀번호를 다시 입력)
- 종료 시각은 잠금 이후에도 연장할 수 있다. 단 종료 후 접근 허용 기간이 끝나 문제파일 키가 폐기되기 전까지만 가능하다. 연장하면 잠금이 풀리고 타임라인 확정본은 폐기되며, 다시 종료될 때 새로 만들어진다.

### 3. 워크스페이스 페이지와 타임라인 페이지, 처음부터 둘 다 존재

대회 종료 시점에 맞춰 작업 화면을 타임라인 화면으로 자동 전환하는 방식은 구현이 복잡해서 빼기로 했다. 대신 **워크스페이스 페이지와 타임라인 페이지가 처음부터 각각 독립적으로 존재**하고, nav에 항상 둘 다 노출된다. 참가자는 대회 중이든 종료 후든 원하는 화면을 그때그때 골라 들어간다.

- 대회 진행 중: 워크스페이스에서 코드 작업. 타임라인 페이지에는 "종료 후 제공" 안내만 보인다.
- 대회 종료 후: 워크스페이스는(2번 항목에 따라) 읽기 전용 상태가 되고, 타임라인은 종료 직후 자동으로 집계된 확정본을 보여준다.

**타임라인 확정본**: 대회 종료 후에만 만들어진다. 수정 이력과 함께 수정 요청의 결과(반영·취소·무효), 팀장 강제 적용 표시, 브랜치 병합 이력, 풀이 완료 표시 변경이 들어간다. 집계는 잠금 직후 마스터 키 없이 수행되므로, 수정 이력 메타데이터(작성자·시각·수정 메시지·변경 파일 경로)는 평문으로 저장하고 파일 내용과 메모만 암호화한다.

**타임라인 UI 방식**: 가운데 세로선(스파인)을 기준으로 로그가 좌우 번갈아 붙는 방식. 각 로그는 스파인에서 뻗어나온 박스로 표시되고, 박스 안에는 시간 등 메타데이터와 로그 설명이 들어간다. (사이드바의 "로그 페이지"는 이것과 별개로, 레포별 커밋 로그를 보여주는 좀 더 전통적인 리스트 형태로 유지)

> 처음엔 "라이트업을 완성된 형태로 자동 생성"까지 욕심냈지만, 생성물의 완성도를 계속 보장해야 하는 부담이 커서 **"라이트업 쓸 때 참고하는 힌트·타임라인"** 정도로 스코프를 좁혔다.

### 4. 코드·문제파일 암호화 *(확정 스택: Argon2id + Redis)*

**팀 코드**: 팀장이 정한 워크스페이스 비밀번호로 실제 암호화 키(마스터 키)를 만든다. 비밀번호를 그대로 키로 쓰지 않고 Argon2id(일부러 느리고 메모리를 많이 쓰도록 설계된 함수)에 통과시켜서 만드는데, 이렇게 하면 공격자의 무차별 대입 시도가 크게 어려워진다.

이렇게 만든 마스터 키는 DB 어디에도 저장하지 않는다. DB엔 이 계산에 필요한 재료값(salt)과, 비밀번호가 맞는지 확인하기 위한 용도로 아무 의미 없는 고정 문구 하나를 이 마스터 키로 암호화해둔 "확인값"만 저장한다. 로그인 시 입력받은 비밀번호로 같은 계산을 다시 돌려 마스터 키를 재계산하고, 그 키로 확인값을 열어보는 데 성공하면 비밀번호가 맞다는 뜻이 된다 — 쓰는 암호화 방식(AES-256-GCM) 자체에 위조 방지 기능이 내장돼 있어서, 시그니쳐를 직접 검사하는 로직을 따로 짤 필요가 없다.

검증까지 마친 마스터 키는 서버 쪽 세션 저장소(Redis)에 로그인 세션(SID)과 워크스페이스에 연결해 캐싱해두고, 사용자 브라우저에는 마스터 키가 아니라 의미 없는 로그인 세션 ID만 쿠키로 내려준다(HttpOnly·Secure·SameSite). 워크스페이스 접근용 별도 세션·토큰은 없으며, 마스터 키의 TTL은 로그인 세션 만료(3일)를 따른다. 비밀번호를 입력하는 곳은 워크스페이스 참가 화면(최초 접속, 또는 마스터 키 캐시가 없을 때의 첫 접근)뿐이다. 마스터 키는 로그아웃·세션 만료 때 폐기되고, 대회가 종료되면 해당 대회 워크스페이스의 마스터 키 캐시를 즉시 폐기한다.

> 마스터 키가 있다고 곧바로 데이터를 보여줘도 되는 건 아니다. "이 요청자가 진짜 이 팀 소속이 맞는지" 확인하는 절차(접근 권한 검증/IDOR 방어)는 암호화와 완전히 별개로 항상 함께 필요하다.

> 워크스페이스가 생성돼도, 팀장이 비밀번호를 설정하기 전(=DB에 salt·확인값이 생기기 전)까지는 어떤 파일 생성·수정도 처리할 수 없다. 비밀번호 미설정 상태를 별도 상태값으로 관리해 관련 API를 명시적으로 막아둬야 한다.

> 워크스페이스 비밀번호는 계정 비밀번호와 같은 정책(8자 이상 128자 이하, 대/소문자·숫자·특수문자 포함)을 따른다. 팀장이 설정한 직후에는 비밀번호를 다시 입력하지 않고 바로 접근되며, 팀장이 설정하기 전에 팀원이 접속하면 "설정 대기 중" 안내가 보인다.

> **알려진 한계**: 이 구조는 DB나 서버 디스크가 통째로(정적으로) 유출되는 경우엔 비밀번호 없이 절대 못 여는 걸 보장한다. 다만 서버가 실시간으로 침투당해(RCE) 그 순간 활성화된 세션의 메모리까지 함께 털리면, 그 세션에 한해 마스터 키가 노출될 수 있다. HSM/TEE 같은 하드웨어 수준의 격리는 스코프 밖으로 판단해, 로그아웃·세션 만료·대회 종료 시 마스터 키를 즉시 폐기하는 선에서 노출 범위를 최소화하기로 했다. (마스터 키는 로그인 세션 TTL 3일 동안만 캐싱)

> 마스터 키가 비밀번호에서 직접 유도되는 구조라 **워크스페이스 비밀번호를 잃어버리면 그 팀의 데이터는 복구할 방법이 없다.** 이건 의도적인 결정이며, **워크스페이스 비밀번호는 재설정을 지원하지 않는다.** 반면 **로그인용 사용자 계정 비밀번호**는 이메일 인증을 거쳐 통상적인 방식으로 재설정할 수 있다 — 단순 로그인 인증이라 데이터 암호화 키와는 무관하기 때문이다. UI 문구에서도 이 둘을 헷갈리지 않게 명확히 구분해야 한다.

**문제파일**: 팀 코드와는 다른 구조를 쓴다. 문제파일은 어차피 대회 참가자 전원에게 공개되는 자료라, 팀별로 다른 키를 쓸 이유가 없다. 그래서 **대회(CTF) 단위로 마스터 키 하나**만 두고, 이 키는 사람이 입력하는 비밀번호 없이 **서버가 대회 생성 시 랜덤으로 생성해서 자체 관리**한다.

- 대회 생성 시 서버가 문제파일용 마스터 키를 자동 생성
- 참가자는 별도 비밀번호 입력 없이 로그인만 하면 문제파일 열람 가능
- 문제파일은 호스트가 문제를 등록(업로드)할 때 이 키로 암호화된다. 참가자가 문제를 워크스페이스에 추가하면 문제 파일 영역에 그대로 복사되고, 팀 풀이 영역으로 복사할 때 워크스페이스 키로 다시 암호화된다.
- 이 키의 유효 기간은 **해당 CTF의 종료 시각 + 종료 후 접근 허용 기간**까지다. 접근 허용 기간(일)은 호스트가 CTF 설정에서 정하며, 기간이 지나면 키를 폐기해 문제 파일 영역은 더 이상 열 수 없다. (팀 코드는 워크스페이스 키라 그대로 열림)
- 트레이드오프: 팀 코드용 키와 달리 서버가 키를 직접 들고 있으므로, 서버가 대회 진행 중 실시간으로 침투당하면(RCE) 문제파일도 함께 노출될 수 있다. 다만 문제파일은 원래 대회 종료 후 사실상 공개되는 자료라 이 정도 노출 리스크는 감수 가능하다고 판단했다.

**암호화 대상 정리**: 팀 코드·파일 메모는 워크스페이스 마스터 키로, 문제 파일은 CTF 마스터 키로 암호화한다. 파일 경로(파일 이름·폴더 구조)와 수정 이력 메타데이터는 암호화하지 않는다.

### 5. 주최측 모니터링 대시보드

대회 진행 중 주최측이 참가팀들의 실시간 풀이 진행 상황(어떤 문제에 몇 팀이 붙어있는지, 진행률 등)을 한눈에 볼 수 있는 대시보드. 대회 종료 후 라이트업만으로는 파악할 수 없었던 참가자 인사이트를 대회 중에 바로 얻을 수 있다는 게 핵심 가치이자, CTFNote와의 결정적 차별점이다.

- 대회 시간 진행률 (경과·남은 시간)
- 문제별 시도한 팀 수·푼 팀 수 — 시도는 그 문제를 워크스페이스에 추가한 팀, 푼 팀은 팀이 직접 표시하는 "풀이 완료 표시"(자가 체크) 기준이다. 플래그를 제출해 채점하는 것이 아니므로 자기 신고 값이다.
- 팀별 시도한 문제 수·풀이 완료로 표시한 문제 수, 팀 활동 로그(이벤트 종류·시각·작성자·대상 파일 경로 등 메타데이터)
- 호스트에게는 통계와 메타데이터만 노출된다. 팀 코드·메모·수정 메시지는 볼 수 없다(팀 비밀번호로 암호화되어 주최측도 복호화할 수 없음).
- 진행 중 갱신은 폴링으로 한다. 대회 종료 후에는 "CTF 총 요약"이 종료 시점 확정본을 보여준다.

## API 응답 규칙

### 이름 규칙

- 코드(변수·필드·메서드)는 **camelCase를 써야만 한다** (`userId`).
- JSON은 편의성을 위해 **snake_case로 통일**한다 (`user_id`). 요청·응답 모두 해당.

### 응답 형식

응답은 성공과 에러 두 가지다. `success`로 구분한다.

**성공**

```json
{
  "success": true,
  "message": "로그인 성공",
  "data": {
    "id": 1,
    "email": "EAsports@gmail.com",
    "username": "nexon"
  }
}
```

**에러**

```json
{
  "success": false,
  "error_code": "AUTH_FAILED",
  "message": "이메일 또는 비밀번호가 올바르지 않습니다."
}
```

> 위 예시는 "이런 식으로 쓰자"는 형식 예시이며, 실제 필드 구성(`id` 노출 방식 등)은 각 API에서 정한다.

> 로그인 실패는 이메일이 없을 때와 비밀번호가 틀렸을 때 **같은 메시지**를 쓴다. 가입 여부를 알려주면 공격자가 계정 존재 여부를 확인할 수 있다(계정 열거).

### 그 외 규칙

- HTTP 상태코드는 200만 쓰지 않고 실제 상태에 맞게 사용한다 (400/401/403/404/409 등). `success`는 그대로 유지.
- `error_code`는 대문자 스네이크 + 도메인 접두어 (`AUTH_FAILED`, `TEAM_NOT_FOUND`). 목록은 한 곳에서 관리.
- `data`가 없을 때도 필드를 빼지 않고 `null`로 항상 포함.
- 입력값 검증 실패: `error_code`는 `VALIDATION_FAILED`, 필드별 오류는 `errors: [{"field": "email", "message": "..."}]`. `errors`는 검증 실패일 때만 포함하고 다른 에러에서는 필드 자체를 뺀다.
- 목록 응답: `data: { "items": [...], "page": 1, "size": 20, "total_count": 53 }`. `page`는 1부터 시작.
- 날짜는 ISO 8601로 시간대까지 표기 (`2026-09-29T10:30:00+09:00`).

```
        │   ├── 파일 이동·복사·메모
        │   ├── 풀이 완료 표시
        │   ├── 브랜치 탭 (생성·삭제·병합)
        │   └── 로그 페이지
        ├── 풀 문제 추가
        └── 타임라인 및 요약
```

> 워크스페이스와 타임라인은 별도 페이지지만 참가자 nav에 항상 함께 노출된다. 대회 종료 여부에 따라 화면이 자동으로 전환되는 방식은 채택하지 않았다.
>
> "문제 폴더 선택"·"풀 문제 폴더 추가" 같은 이름은 화면 이름일 뿐이며, 데이터로서의 폴더는 없다.

## 역할별로 할 일

- **프론트 (1명)**: 참가팀용 대시보드/레포/타임라인 화면 + 주최측용 모니터링 대시보드 UI 제작 (레포 브라우저는 파일 경로를 `/`로 잘라 폴더 트리로 렌더링, 코드 뷰어, 동의 요청 알림 UI 포함)
- **백엔드 (3명)**: 공동 작업 구조 구현(동의 기반 수정·웹소켓 실시간 포함), 팀·대회·주최측 계정 데이터 관리(팀 등록 시 워크스페이스 자동 생성), 대회 종료 시각에 맞춰 작업 제한 기능, 작업 기록을 타임라인 및 주최측 모니터링 데이터로 가공하는 로직
- **보안 (2명)**: 아래 참고

### 보안팀이 할 일

이 프로젝트에서 뼈대 자체를 보안팀(2명)이 설계할 예정.

**데이터 보호 설계** — 서버에 저장되는 팀 코드·문제파일을 암호화하는데, 단순히 "암호화 기능 하나 붙이기"가 아니라 언제 잠그고 언제 열어주는지, 서버가 해킹당해도 내용이 새지 않으려면 어떤 구조여야 하는지를 처음부터 설계한다. 이 설계에 따라 백엔드·프론트 구조도 같이 바뀜.

**접근 권한 검증** — 우리 팀만 봐야 하는 데이터를 다른 팀이 URL만 바꿔서 몰래 볼 수 있는 구멍이 없는지 전체 점검. 제3자 유출 방어라는 원래 가치관에 더해, **타팀 간 협업 차단**이라는 핵심 셀링포인트 자체를 지탱하는 부분이라 더욱 필수적이다. 웹소켓도 예외가 아니다 — 연결할 때뿐 아니라 메시지마다 소속·잠금 여부를 다시 확인하고, Origin을 검사하며, 마스터 키는 소켓으로 내려보내지 않는다.

**자체 침투 테스트** — 팀 내부에서 직접 뚫어보는 모의 해킹을 거치고, 취약점 피드백 후 패치.

> 이 세 가지 결정이 프로젝트 초반부터 계속 다른 파트 설계에 영향을 주기 때문에, 보안팀은 마지막이 아니라 기획 단계부터 끝까지 계속 관여하는 구조로 진행.

## 보안 지식, 얼마나 알아야 하나

**우리가 하는 건 전부 "이미 검증된 부품을 조립"하는 것이지, 새로운 보안 이론을 만드는 게 아니다.**

| 무섭게 들리는 이름 | 실제로 하는 일 | 필요한 새 지식 |
|---|---|---|
| "강력한 암호화" | 표준 암호화 라이브러리 함수 호출 (언어 기본 crypto 모듈에 이미 있는 것) | 알고리즘 원리를 이해할 필요 없음. "이 함수에 이렇게 넣으면 이렇게 나온다"만 알면 됨 |
| "IDOR 방어" | 매 API 요청마다 "이 사람이 이 팀 소속 맞나?" 확인하는 로직 | 개발 단계에서 가능한 한 최대한 막으면 좋지만, 보안 리뷰를 통해 알려준 부분을 패치하는 걸로도 진행 가능 |
| "실시간 협업 (CRDT)" | 검증된 오픈소스 라이브러리를 편집기에 붙이는 작업 | CRDT 이론을 몰라도 됨. 컴포넌트 붙이듯 조립 |

즉 이 프로젝트에서 "새로 공부해야 하는 것"은 암호학 이론이 아니라 **"라이브러리 문서 읽는 법"**이다.

### 역할별로 실제 필요한 공부량

- **백엔드**: 지금까지 해오던 API 서버 개발 + 라이브러리 문서 읽기. 암호화는 함수 호출 수준.
- **보안**: CTF에서 쓰던 웹 취약점 진단 능력을 방어자 입장으로 뒤집어 적용. 이미 갖고 있는 스킬을 새 방향으로 쓰는 것.
- **프론트**: 평소 하던 UI 개발 + 오픈소스 컴포넌트(코드 하이라이팅 등) 연동.
- **PM**: 팀 조율, 필요시 실제 CTF 커뮤니티·멘토와 정책 협의.

> **한 줄 정리**: 이 프로젝트가 요구하는 건 "새로운 보안 전문가가 되는 것"이 아니라 "이미 있는 도구들을 우리 문제에 맞게 잘 골라 조립하는 엔지니어링"이다.

## 스코프 정리

### 꼭 있어야 함 (MVP)

- 계정 시스템 (SaaS 온보딩 — 회원가입, 로그인, 마이페이지. 호스트/참가자 역할 구분 없이 CTF를 만든 계정이 호스트, 계정당 CTF 최대 3개)

- 종료 후 자동 잠금
- 워크스페이스 페이지 + 타임라인/힌트 페이지 (상시 공존, 타임라인은 종료 후 확정본)

- 풀이 완료 표시 (팀 자가 체크)
- 기본 UI (레포 브라우저, 코드 뷰어)
- 주최측 모니터링 대시보드
