## 읽는 법

- 입력·출력 필드는 JSON 기준 snake_case다. "출력"은 응답의 `data` 안에 들어가는 필드이고, 응답 래핑(`success`/`message`/`data`)은 README "API 응답 규칙"을 따른다.
- 타겟: **공통** / **호스트**(CTF를 만든 계정) / **참가자**(팀에 등록된 계정). 계정 타입 구분은 없다.
- "소속 검증": 요청자가 그 `workspace_id`(또는 `ctf_id`) 팀원/호스트인지 **매 요청** 확인한다. 실패는 `403`이지만 존재 노출 방지를 위해 `404`로 응답해도 된다.
- 쓰기 요청은 모두 잠금 검사를 먼저 한다 → [종료 후 수정 불가](#종료-후-수정-불가).
- 비밀번호가 필요한 곳은 [워크스페이스 참가](#워크스페이스-참가)뿐이다. 그 외 파일 API는 비밀번호를 받지 않고, 세션에 마스터 키가 없으면 `401`로 응답해 그리로 유도한다.
- 워크스페이스 `password_status = unset`인 동안 암호화가 필요한 요청(파일 생성·수정, 풀 문제 추가 등)은 `409`로 명시적으로 막는다.
- 파일 경로 규칙: `/`로 계층 구분. 앞뒤 `/`, 연속 `//`, 빈 세그먼트, `.`/`..` 세그먼트, 제어 문자 금지. 세그먼트당 255자, 전체 1024자. 같은 (워크스페이스, 브랜치, 문제, 영역) 안에서 유일하고, 다른 파일의 폴더 경로와 겹칠 수 없다. 위반 시 `400`(겹침·중복은 `409`).
- 성공 응답은 `204`를 쓰지 않는다. "본문 없음"으로 적힌 항목은 `200`(생성이면 `201`) + `data: null`이다.
- `team_id`는 `workspace_id`와 같은 값이다 (팀 1 = 워크스페이스 1, 별도 team 테이블 없음).
- 모든 ID는 UUID다. 유저 ID(`user_id`)는 응답에 노출하지 않고 유저는 `email`/`username`으로 식별한다.
- 반영 모델: 파일 생성·이동·복사·메모·풀이 완료 표시는 **즉시 반영**. 파일 수정·삭제·브랜치 삭제는 **동의 플로우**. 브랜치 병합은 **팀장 동의만**.

## 계정·인증

공통 사항: 인증은 **세션 쿠키 `SID`**(HttpOnly·Secure·SameSite)로 통일했다. 로그인 식별자는 **이메일**이며 별도 `login_id`는 없다. 계정에 호스트/참가자 역할은 없다. 가입 시 이메일 인증은 하지 않는다 (알려진 한계: 남의 이메일로 선점 가입한 계정이 있을 수 있어, 호스트가 팀원을 등록할 때 본인 확인이 필요하다).

### 회원가입
`공통 · auth · 소개 페이지, 회원가입`
- 흐름: 유효성 검사 → `email` 중복 검사 → 비밀번호 Argon2 해싱 → DB 저장. **가입해도 세션을 만들지 않는다** (자동 로그인 없음, 로그인은 별도 호출). 서버는 302 리다이렉트를 하지 않고 화면 이동은 프론트 라우팅이 한다.
- 입력: `email`(varchar 255, unique, 필수, `@`와 도메인 필수), `password`(필수, 8자 이상 128자 이하, 대/소문자+숫자+특수문자), `password_confirm`(필수), `username`(varchar 20, 필수, 2~20자).
- 출력: `201 Created` — `email`, `username`. **`user_id`는 포함하지 않는다.**
- 예외: `400` 유효성 실패·필수 누락 / `409` 이메일 이미 존재.
- 비고: 비밀번호 상한 128자는 과도한 입력 방지용이고 해시로 저장하므로 짧은 상한은 두지 않는다.

### 로그인
`공통 · auth · 소개 페이지, 로그인`
- 흐름: 이메일로 유저를 찾고 입력한 비밀번호를 저장된 해시와 대조한다.
- 입력: `email`(필수), `password`(필수, 형식 검증은 하지 않고 해시 대조만).
- 출력: `200 OK` — `SID` 쿠키 발급.
- 예외: `400` 필수 누락 / `401` 없는 이메일 **또는** 비밀번호 불일치 (같은 메시지, 계정 열거 방지) / `429` 로그인 실패 횟수 초과.
- 비고: 세션 만료 3일. **이 `SID` 하나로 워크스페이스 접근까지 처리**한다(별도 워크스페이스 세션·토큰 없음). 워크스페이스 참가에 성공하면 마스터 키가 이 세션에 연결되어 캐싱된다(TTL은 세션을 따름). Rate limit: 같은 이메일(또는 IP)에서 15분 안에 5회 실패 → 15분간 `429`.

### 비밀번호 찾기
`공통 · auth · 로그인`
- 흐름: 이메일로 본인 확인 후 재설정 링크를 보낸다.
- 입력: `email`(필수, 재설정 링크를 받을 계정 이메일).
- 출력: `200 OK` — 본문 없음. 해당 이메일로 재설정 링크 메일 발송.
- 예외: `400` 이메일 형식 오류 / `200` 계정이 없어도 동일 응답(존재 여부 노출 방지) / `429` 과다 요청.
- 비고: 계정 존재 여부와 관계없이 항상 같은 응답. 링크 유효시간 5분.

### 비밀번호 재설정
`공통 · auth · 로그인`
- 흐름: "비밀번호 찾기" 메일 링크로 이메일 인증을 마친 유저가 새 **계정 비밀번호**를 입력하면 정책 검증 후 Argon2로 저장한다. **워크스페이스 비밀번호는 바뀌지 않는다.**
- 입력: `reset_token`(필수, 5분 유효), `new_password`(필수, 가입과 같은 정책), `new_password_confirm`(필수).
- 출력: `200 OK` — 본문 없음.
- 예외: `400` 유효성 실패 / `410 Gone` 토큰 만료.

### 로그아웃
`공통 · auth · 로그인, 대시보드`
- 흐름: 로그인 상태에서 `SID`로 세션을 확인하고 삭제한다.
- 입력: 없음 (`SID` 쿠키로 식별).
- 출력: `200 OK` — `data: null`.
- 예외: `400` 로그아웃 실패 시.
- 비고: 세션 무효화 후 삭제. 이 세션에 연결된 **워크스페이스 마스터 키 캐시(Redis)를 즉시 파기**하고 해당 세션의 WebSocket 연결도 종료한다.

### 유저 정보 출력
`공통 · data · 마이페이지`
- 흐름: `SID`로 유저를 식별해 프로필을 반환한다.
- 입력: 없음.
- 출력: `200 OK` — `email`, `username`, `created_at`. 비밀번호(해시 포함) 등 민감 정보와 `user_id`는 포함하지 않는다.
- 예외: `401` 세션 없음·만료.
- 비고: 본인 조회 전용. 다른 유저 프로필 조회(예: 팀원 목록의 닉네임)가 필요하면 별도 기능으로 논의한다.

### 유저 정보 수정
`공통 · user · 마이페이지`
- 흐름: 마이페이지에서 닉네임·비밀번호를 선택적으로 수정한다(PATCH, 부분 업데이트). 비밀번호를 바꿀 때는 현재 비밀번호를 재확인한다.
- 입력: `username`(선택, 2~20자), `current_password`(조건부 — `new_password`를 바꿀 때만 필수), `new_password`(선택, 가입과 같은 정책).
- 출력: `200 OK` — `email`, `username`. 비밀번호는 응답에 포함하지 않는다.
- 예외: `current_password` 불일치 `401` / 형식 오류·필수 누락 `400`.
- 비고: 로그인 식별자 `email`은 이 기능으로 변경할 수 없다. 여기서 바꾸는 것은 **계정 비밀번호**이고, 워크스페이스 비밀번호는 변경·재설정을 지원하지 않는다(UI 문구에서 둘을 구분).

### 대시보드 목록 조회
`공통 · data · 대시보드` — Claude 검토(2026-09-20)에서 추가된 제안 항목. 팀 확정 전.
- 흐름: 호스트는 내가 만든 CTF 목록을, 참가자는 내가 속한 팀·워크스페이스 목록을 본다.
- 입력: 없음 (세션으로 식별).
- 출력: `200 OK` — `hosted_ctfs[]`(`ctf_id`, `name`, `status`: `upcoming`/`running`/`ended`), `workspaces[]`(`workspace_id`, `team_name`, `ctf_name`, `password_status`: `set`/`unset`, `workspace_status`: `open`/`locked`).
- 예외: `401` 미로그인.
- 비고: 세션 기준으로만 조회해 다른 유저·팀 데이터가 섞이지 않게 한다.

## 호스트: CTF

### CTF 생성
`호스트 · host · 대시보드, CTF 설정` — Claude 추가 행(2026-09-20), 검토 필요.
- 흐름: 로그인한 사용자가 새 CTF를 만들고 그가 호스트가 된다. **계정당 최대 3개(종료된 것 포함).** 서버가 문제 파일용 CTF 마스터 키를 자동 생성한다(`end_at + access_days_after_end`까지 유효).
- 입력: `name`(필수), `start_at`(선택), `end_at`(필수), `access_days_after_end`(필수, ≥0), `team_size_limit`(선택, 미설정 시 무제한), `description`(선택).
- 출력: `201 Created` — `ctf_id`, `name`, `start_at`, `end_at`, `access_days_after_end`, `team_size_limit`, `description`. **CTF 마스터 키는 응답·로그에 포함하지 않는다.**
- 예외: `400` 필수 누락·`end_at < start_at`·`access_days_after_end < 0` / `401` 미로그인 / `403` 생성 한도(3개) 초과.
- 비고: Jeopardy 형식만 지원(MVP).

### CTF 설정 기능
`호스트 · host · CTF 설정`
- 흐름: 호스트가 자기 CTF의 기본 정보를 설정·수정한다. `end_at`은 워크스페이스 자동 잠금의 기준 시각이다.
- 입력: `ctf_id`(필수), `name`(필수), `start_at`, `end_at`(필수), `access_days_after_end`(필수), `team_size_limit`, `description`.
- 출력: `200 OK` — 위 필드 그대로.
- 예외: `400` `end_at < start_at`·`access_days_after_end < 0`·필수 누락 / `409` 접근 허용 기간이 지나 CTF 마스터 키가 폐기된 뒤 `end_at` 연장 시도.
- 비고: 호스트만 가능(해당 CTF의 호스트인지 매 요청 검증). 시작 전에는 자유 수정, 시작 후에는 `end_at` 연장 정도만 허용하는 방식을 제안. `end_at`을 바꾸면 잠금 기준과 문제파일 키 유효기간(`end_at + access_days_after_end`)도 같이 갱신된다. **이미 잠긴 뒤에도 연장할 수 있다**(키 폐기 전까지). 연장으로 종료 시각이 다시 미래가 되면 워크스페이스는 `locked → open`이 되고, 타임라인·총 요약은 다시 `409`(진행 중)가 되며 재종료 후 새로 계산된다. 마스터 키 캐시는 이미 폐기됐으므로 팀은 비밀번호를 다시 입력한다. `access_days_after_end`가 지나면 문제 파일 영역은 더 이상 열 수 없지만, 팀 코드와 타임라인은 이 설정과 무관하게 계속 열람된다.

### 문제 등록
`호스트 · host · CTF 설정`
- 흐름: 호스트가 문제 기본 정보와 파일을 사전 등록한다. 서버가 검증하고 **CTF 마스터 키로 암호화**해 저장한다("암호화 저장"은 참가자·호스트 공통 로직이며 여기서는 `ctf_id`/`problem_id` 기준으로 호출).
- 입력: `ctf_id`(필수), `title`(필수), `category`(필수, Web/Pwn/Crypto 등), `description`(필수), `files`(선택, 문제 파일).
- 출력: `201 Created` — `problem_id`, `title`, `category`, `description`.
- 예외: `404` 없는 `ctf_id` / `403` 호스트 아님 / `400` 필수 누락·허용되지 않는 파일 형식·크기 초과·경로 규칙 위반 / `409` 중복 문제 / `500` 저장 오류.
- 비고: 대회 시작 전에 사전 등록. 문제는 해당 CTF에 종속되고 다른 CTF에서 접근 불가. 업로드한 파일 이름이 그대로 문제 파일 영역의 `file_path`가 된다(`/`가 있으면 폴더로 렌더링).

### 문제 관리 (조회/수정/삭제)
`호스트 · host · CTF 설정`
- 흐름: 호스트가 등록한 문제 목록을 조회하고 정보·파일을 수정하거나 삭제한다. 파일을 교체하면 CTF 마스터 키로 다시 암호화한다.
- 입력: `ctf_id`(필수), `problem_id`(수정·삭제 시 필수), `title`/`category`/`description`/`files`(수정 시 바꿀 필드만).
- 출력: 조회 `200` — `problems[]`(`problem_id`, `title`, `category`, `description`, 문제 파일 목록) / 수정 `200` — `problem` / 삭제 `200` — `data: null`.
- 예외: `403` 호스트 아님 / `404` 없는 `ctf_id`·`problem_id`.
- 비고: **대회 시작 전에만 수정·삭제 가능, 시작 후에는 조회만**(시작 후 수정·삭제는 `409`). 참가팀 워크스페이스에 이미 복사된 사본과 원본이 어긋나는 것을 막기 위한 단순화.

### 팀/유저 등록
`호스트 · host · 참가자 관리`
- 흐름: 호스트가 팀과 팀원(이메일)을 등록하고 팀장을 함께 지정한다. **이미 가입된 이메일만** 등록할 수 있다. 팀 등록과 함께 팀 이름의 워크스페이스가 **같은 요청 안에서** 만들어진다([워크스페이스 지정](#워크스페이스-지정)). 워크스페이스 생성이 실패하면 팀 등록도 롤백한다.
- 입력: `ctf_id`(필수), `team_name`(필수, 같은 CTF 안에서 unique), `member_emails`(필수, 가입된 계정만), `leader_email`(필수, `member_emails` 중 한 명).
- 출력: `201 Created` — `team_id`, `team_name`, `workspace_id`, `members[]`(`email`, `username`, `is_leader`).
- 예외: `400` 가입되지 않은 이메일 포함·`leader_email`이 목록에 없음·`team_size_limit` 초과 / `409` 같은 CTF의 다른 팀에 이미 등록된 유저 포함.
- 비고: 호스트 권한은 매 요청 검증. 팀장은 워크스페이스 비밀번호 최초 설정·병합 동의·강제 적용의 주체이며 **팀장을 바꾸는 기능은 없다**. 유저 식별자는 이메일.

### 워크스페이스 지정
`호스트 · host · 참가자 관리` — 별도 호출이 아니라 "팀/유저 등록"의 같은 요청 안에서 처리된다.
- 흐름: 팀 이름으로 격리된 워크스페이스(레포)를 만든다. 메인 브랜치 `main`을 함께 만든다(삭제 불가). 생성 시 `password_status = unset`, `workspace_status = open`.
- 입력: `ctf_id`, `team_id`, `team_name` ("팀/유저 등록"에서 그대로 사용).
- 출력: 내부 처리 — `workspace_id`, `workspace_status`(`open`), `password_status`(`unset`). `workspace_id`는 "팀/유저 등록" 응답에 담긴다.
- 예외: 별도 응답 없음. 실패하면 팀 등록과 함께 롤백.
- 비고: **워크스페이스 1 = 팀 1 = 레포 1.** 다른 팀의 `workspace_id`로 접근을 시도해도 절대 접근되지 않도록 매 요청 소속 검증.

## 호스트: 모니터링

### 모니터링 집계 (진행 현황)
`호스트 · data · 모니터링`
- 흐름: 호스트가 대시보드를 열면 서버가 그 CTF의 현황을 계산해 반환한다. 실시간 갱신은 **클라이언트 폴링**.
  - 대회 시간: 경과·남은 시간, 진행률 = (`now`−`start_at`)/(`end_at`−`start_at`). 시작 전 0%, 종료 후 100%. `start_at`이 없으면 진행률은 계산하지 않고 남은 시간만 반환.
  - 문제별: 시도 팀 수(문제를 워크스페이스에 추가한 팀), 풀이 팀 수(풀이 완료로 표시한 팀 — **자기 신고 값**).
  - 팀별: 시도한 문제 수, 풀이 완료로 표시한 문제 수.
- 입력: `ctf_id`(필수).
- 출력: `200 OK` — `contest`(`start_at`, `end_at`, `elapsed_seconds`, `remaining_seconds`, `progress_percent`), `problems[]`(`problem_id`, `title`, `category`, `attempted_team_count`, `solved_team_count`), `teams[]`(`team_id`, `team_name`, `attempted_count`, `solved_count`).
- 예외: `401` / `403` 호스트 아님 / `404` 없는 `ctf_id`.
- 비고: 호스트에게는 통계·메타데이터만. 팀 코드·메모는 포함하지 않는다. 종료 후 확정 집계는 "CTF 총 요약"이 재사용한다.

### CTF 총 요약
`호스트 · summary · CTF 총 요약`
- 흐름: 대회 종료 후 "모니터링 집계"와 같은 계산을 종료 시점 기준으로 반환한다. **저장된 확정본은 없고 조회 시 계산한다**(종료 후에는 쓰기가 막혀 입력이 변하지 않으므로 결과가 같다. 단 종료 후 팀 등록 허용 여부는 미결정 — [erd.md 미결정 2](erd.md#미결정-사항)). 대회 시간(시작·종료·총 시간), 문제별 시도·풀이 팀 수, 팀별 시도·풀이 문제 수. 팀별 타임라인은 호스트가 코드를 볼 수 없으므로 제공하지 않는다. `end_at` 연장으로 다시 열리면 `409`가 되고 재종료 후 다시 계산된다.
- 입력: `ctf_id`(필수).
- 출력: `200 OK` — `contest`, `problems[]`, `teams[]` (모니터링 집계와 같은 구조).
- 예외: `401` / `403` 호스트 아님 / `404` / `409` 아직 종료되지 않은 CTF.
- 비고: "푼 팀"은 자가 체크라 정확한 채점 결과가 아니다.

## 로그

로그는 `log` 테이블 하나를 공유하고 조회 시 `workspace_id`로 필터링한다 → [erd.md](erd.md#log).

### 로그 집계
`공통 · data · 모니터링, 로그 페이지`
- 흐름: 별도 API 호출 없이 **각 기능이 수행될 때 서버 내부에서 자동으로 이벤트를 기록**한다. 호스트용 집계에는 워크스페이스 참가(`workspace_join`), 브랜치 생성/삭제/병합, 파일 생성/삭제/수정/이동/복사, 수정 요청·동의·강제 적용, 풀이 완료 표시, 시스템 이벤트(워크스페이스 잠금 등, 행위자 없음)가 포함된다. **로그인은 기록하지 않는다**(특정 워크스페이스에 속하지 않기 때문). 참가자는 자기 워크스페이스 활동만.
- 입력: 없음. 출력: 내부 처리(API 응답 없음).
- 예외: 로그 기록이 실패해도 **원래 요청은 실패시키지 않는다.** 기록 실패는 별도로 재시도·알림 처리해 로그 장애가 서비스 장애로 번지지 않게 한다.
- 비고: 호스트 대시보드는 폴링(동의 플로우는 WebSocket).

### 로그 출력
`공통 · data · 모니터링, 로그 페이지`
- 흐름: 호스트는 전체 팀 로그를 팀·시간대·이벤트 종류로 필터링해 조회한다. 참가자는 자기 워크스페이스 로그만 조회한다(다른 팀 로그 조회 불가, IDOR 방지).
- 입력: 참가자는 `workspace_id`(필수). 호스트는 `ctf_id`(필수)와 `team_id`(선택, 팀 하나로 필터, 미지정 시 전체 팀). 공통으로 `event_type`, `from`/`to`(둘이 함께).
- 출력: `200 OK` — `logs[]`(`team_id`, `username`, `event_type`, `timestamp`, `detail`). 내부 PK는 노출하지 않는다.
- 예외: `400` 잘못된 필터·`from > to`·`from`/`to` 하나만 / `404` 없는 `team_id`·`workspace_id`, **다른 팀 워크스페이스 조회(본래 403이지만 보안상 404)**.
- 비고: 호스트에게 노출되는 `detail`은 메타데이터(이벤트 종류·시각·작성자·대상 파일 경로/브랜치명/문제)만 포함하고 **파일·메모 내용과 수정 메시지는 포함하지 않는다.** 호스트 권한은 매 요청 검증.

## 워크스페이스 접근·보안

### 워크스페이스 비밀번호 설정
`참가자 · user · 워크스페이스 참가`
- 선행 조건: 로그인 상태이고 요청자가 해당 워크스페이스의 **팀장**이며, `password_status = unset`.
- 흐름: 서버가 워크스페이스별 랜덤 `salt` 생성 → 비밀번호+`salt`를 Argon2id에 통과시켜 마스터 키 생성 → 고정 문구를 마스터 키로 AES-256-GCM 암호화해 verifier block 생성 → DB에는 `salt`와 verifier block(과 KDF 파라미터)만 저장하고 `password_status = set`. 비밀번호·마스터 키는 저장하지 않는다. 설정 직후 마스터 키를 Redis에 `(SID, workspace_id)`로 캐싱해 팀장이 비밀번호를 다시 입력하지 않고 접근한다.
- 입력: `workspace_id`(필수), `password`(필수, 8~128자 대/소문자+숫자+특수문자, 계정 비밀번호와 같은 정책), `password_confirm`(필수 — 재설정 불가이므로).
- 출력: `201 Created` — 본문 없음. `salt`·verifier·마스터 키는 응답에 포함하지 않는다.
- 예외: `400` 불일치·정책 위반 / `401` / `403`(소속·팀장 아님, `404` 가능) / `404` / `409` 이미 설정됨 / `423` 잠김.
- 비고: **재설정·변경 불가**(분실 시 복구 불가, 의도된 결정이며 설정 화면에 명확히 안내). 계정 비밀번호와 별개라 UI에서 구분. `unset`인 동안은 파일 생성·수정, 풀 문제 추가 등을 별도 상태값으로 명시적으로 차단. 팀장이 설정하기 전에 팀원이 접속하면 "팀장이 비밀번호를 설정하면 접속할 수 있다" 안내. 비밀번호는 로그·응답에 평문으로 남기지 않고 처리 즉시 메모리에서 폐기.

### 워크스페이스 참가
`참가자 · user · 워크스페이스 참가`
- 선행 조건: 로그인(`SID`) 상태, 서버가 소속을 확인한 상태, `password_status = set`(미설정이면 비밀번호 설정으로 유도, 팀원은 "설정 대기 중" 안내). **소속 확인과 비밀번호 검증은 별개 레이어이며 둘 다 통과해야 한다.**
- 흐름: DB의 `salt`와 입력 비밀번호를 Argon2id에 통과시켜 후보 마스터 키 생성 → 그 키로 verifier block 복호화 시도(GCM 태그 검증 실패 = 비밀번호 틀림) → 성공 시 마스터 키를 Redis에 `(SID, workspace_id)`로 TTL과 함께 캐싱. 클라이언트에는 마스터 키도 별도 토큰도 내려주지 않고 이후 요청은 `SID` 쿠키만 보낸다.
- 입력: `workspace_id`(필수), `password`(필수).
- 출력: `200 OK` — 본문 없음 (새 토큰·쿠키 발급 없음).
- 예외: `401` 비밀번호 틀림(태그 검증 실패) / `403`→`404` 소속 아님 (마스터 키 유무와 무관하게 항상 별도 확인. 빠지면 URL만 바꿔 다른 팀이 접근하는 구멍이 생긴다) / `409` 비밀번호 미설정.
- 비고: KDF는 **Argon2id 고정**, 권장 파라미터 memory 19MB 이상·iterations 2~3·parallelism 1. `salt`는 비밀번호 설정 시 워크스페이스별 랜덤 생성. 마스터 키 TTL은 로그인 세션 만료(3일). `SID`는 의미 없는 랜덤 값이어야 하고 마스터 키를 역산할 수 없어야 한다. 마스터 키는 로그아웃·세션 만료 시 즉시 파기되고, 대회 종료 시에는 해당 CTF 워크스페이스 키만 파기된다(잠긴 뒤 읽기 전용 열람도 이 절차를 다시 거침). 실패 횟수 제한(rate limiting) 권장. 비밀번호가 입력되는 곳은 이 절차뿐. 성공하면 로그에 `workspace_join` 이벤트를 기록한다.

### 암호화 저장
`공통 · security · 문제 풀이, 문제 폴더, CTF 설정` — 참가자(파일 생성·수정 등)와 호스트(문제 등록)가 공통으로 쓰는 내부 로직.
- 흐름: 유효성 검사 → 저장 대상 확인 → 키 결정(팀 코드·메모 = 워크스페이스 마스터 키, 문제 파일 = CTF 마스터 키) → **AES-256-GCM** 암호화 → 암호문과 필요한 메타데이터 저장. 평문은 저장하지 않는다.
- 입력: `workspace_id`(팀 코드 저장 시) 또는 `ctf_id`+`problem_id`(문제 파일 저장 시), `file_id`, `content`.
- 출력: `201 Created` — `file_id`, `success`. 암호화된 내용과 `master_key`는 반환하지 않는다.
- 예외: `400` / `401` 세션 없음 / `403` 소속 아님 / `404` / `409` 저장 충돌 / `423` 잠김 / `500` 암호화·저장 실패.
- 비고: `master_key`는 입력값이 아니다. 클라이언트에서 받지 않고 Redis 세션 캐시에서 꺼낸다(CTF 키는 서버 관리). 마스터 키는 DB에 저장하지 않고 DB에는 `salt`+확인값만 있다. 권한 검증은 키 존재와 별개로 항상 한다. 대회 종료 시 마스터 키 캐시를 폐기(로그인 세션은 유지). 워크스페이스 비밀번호를 잃으면 복구 불가. 파일 경로는 암호화하지 않는다. 암호문 컬럼 포맷은 [erd.md](erd.md#암호문-컬럼-포맷-제안).

### 파일 내용 조회
`참가자 · security · 문제 폴더, 문제 풀이`
- 흐름: 세션 인증 → `workspace_id`·`file_id` 검증 → 소속 검증 → `area`로 복호화 키 결정(문제 파일 영역 = CTF 마스터 키, 서버 관리, `end_at + access_days_after_end` 이후 폐기되면 조회 불가 / 팀 풀이·라이트업 = 워크스페이스 마스터 키) → 암호문 조회 → AES-256-GCM 복호화 → 내용과 메모 반환. 워크스페이스 마스터 키가 Redis에 없으면 `401`로 "워크스페이스 참가" 유도(이 기능은 비밀번호를 받지 않음).
- 입력: `workspace_id`(필수), `file_id`(필수).
- 출력: `200 OK` — `file_id`, `file_path`, `content`, `metadata`, `memo`(복호화됨).
- 예외: `400` / `401` 세션 없음 또는 마스터 키 없음 / `403`→`404` 소속 아님 / `404` / `410` 문제 파일 접근 기간 만료(CTF 키 폐기) / `500` 복호화 실패.
- 비고: **접근 권한 검증과 복호화는 별개.** 로그인했어도 팀원이 아니면 복호화하지 않는다. 잠긴 워크스페이스도 **조회는 허용**(`423` 없음, 단 키 캐시가 폐기돼 "워크스페이스 참가"를 다시 거침). 파일 목록(경로)은 "파일 트리 조회"가 키 없이 제공하고 이 기능은 내용과 메모만 다룬다. IDOR 방어: `workspace_id`/`file_id` 변조로 다른 팀 파일을 못 보도록 매 요청 소속·리소스 관계 검증.

## 문제·파일

세 영역(`problem_files` 문제 파일 / `team_work` 팀 풀이 / `writeup` 라이트업)은 폴더가 아니라 파일의 `area` 값이다. 문제 파일 영역은 호스트가 등록한 원본 그대로 보존되며 **생성·수정·삭제·이동이 모두 금지(`403`)**, 유일하게 "파일 복사"만 허용된다.

### 문제 목록 조회
`참가자 · data · 문제 폴더`
- 흐름: 이번 대회에 등록된 전체 문제 목록을 보고 내 워크스페이스에 이미 추가한 문제인지도 표시한다 ("풀 문제 추가"의 진입점).
- 입력: `workspace_id`(필수), `category`(선택 필터).
- 출력: `200 OK` — `problems[]`(`problem_id`, `title`, `category`, `solve_count`, `solved`, `added_to_workspace`).
- 예외: `401` / `403`→`404` 소속 아님 / `404` 없는 `workspace_id`.
- 비고: `solve_count`·`solved`는 팀 자가 체크 값.

### 풀 문제 추가
`참가자 · competition · 풀 문제 폴더 추가`
- 흐름: 참가자가 목록에서 문제를 골라 워크스페이스에 추가한다. 문제가 `(workspace_id, problem_id)`로 연결되고 3개 영역이 열린다.
  1. 문제 파일 영역: 호스트가 등록한 공식 파일이 **원본 `file_path` 유지, CTF 마스터 키로 암호화된 상태 그대로 복사**된다. 복사 외 조작 금지. 문제 파일 행은 **메인 브랜치에만** 만들고 모든 브랜치에서 보인다.
  2. 팀 풀이 영역: 빈 상태로 시작. 파일 복사로 다른 영역 파일을 가져와 작업.
  3. 라이트업 영역: 빈 상태로 시작.
- 입력: `workspace_id`(필수), `problem_id`(필수).
- 출력: `201 Created` — `problem_id`, `title`, `files[]`(`file_id`, `file_path`; 영역 3개는 고정값이라 ID를 반환하지 않음).
- 예외: `409` 이미 추가된 문제 / `404` 없는 `problem_id` / `423` 잠김 / 소속 아님 `403`→`404`.
- 비고: 전체 문제를 처음부터 넣으면 워크스페이스가 무거워져서 풀 문제를 골라 추가하는 방식. 문제 추가는 모니터링에서 "시도(붙어 있는) 팀"으로 집계된다. 화면에는 3개 영역이 파일이 없어도 항상 표시된다.

### 파일 트리 조회 (레포 브라우저)
`참가자 · data · 문제 폴더, 문제 풀이` — Claude 검토(2026-09-20)에서 추가된 제안 항목.
- 흐름: 문제별 3개 영역의 파일 목록을 경로와 함께 조회한다. 서버는 폴더를 내려주지 않고 `file_path`만 내려주며, 화면이 `/` 기준으로 폴더 트리를 만든다. 어느 브랜치를 조회해도 문제 파일 영역은 메인 브랜치의 행을 함께 돌려준다.
- 입력: `workspace_id`(필수), `branch`(선택, 기본 `main`), `problem_id`(선택).
- 출력: `200 OK` — `files[]`(`file_id`, `problem_id`, `area`, `file_path`, `updated_at`). 폴더 객체는 포함하지 않는다.
- 예외: `401` / `403`→`404` / `404`.
- 비고: 파일 경로는 암호화하지 않으므로 **마스터 키 없이 소속 검증만으로** 가능하다.

### 파일 생성
`참가자 · competition · 로그 페이지, 문제 풀이` — 즉시 반영
- 흐름: 문제의 팀 풀이 또는 라이트업 영역에 새 파일을 만든다. 폴더는 따로 만들지 않고 `file_path`에 `/`를 넣으면 화면에 나타난다. 저장은 "암호화 저장"을 따른다.
- 입력: `workspace_id`(필수), `problem_id`(필수, 이 워크스페이스에 추가된 문제), `area`(필수, `team_work`|`writeup`), `file_path`(필수), `content`(선택, 빈 파일 허용), `branch`(선택, 기본 메인).
- 출력: `201 Created` — `file_id`, `area`, `file_path`.
- 예외: `400` 경로 규칙 위반·잘못된 `area` / `401` 워크스페이스 미인증(마스터 키 없음) / `403` `area = problem_files` (필요하면 "파일 복사"로 사본 생성) / `404` 추가되지 않은·없는 `problem_id` / `409` 같은 경로 존재·폴더 경로와 겹침 / 소속 아님 `403`→`404` / `423` 잠김 / `409` 워크스페이스 비밀번호 미설정.
- 비고: 폴더는 아래에 파일이 있을 때만 보이고 마지막 파일이 삭제·이동되면 사라진다. 폴더 단위 삭제·이름 변경은 없다(하나씩 처리). 경로는 평문.

### 파일 수정
`참가자 · competition · 로그 페이지, 문제 풀이` — 동의 플로우
- 흐름: 수정 요청을 제출하면 서버가 **승인자**(요청 시점에 그 파일을 연 다른 팀원 전원, 보기만 하는 팀원 포함)를 계산한다. 승인자가 없으면 즉시 반영(`200`). 있으면 수정 사항을 pending으로 저장하고 동의를 요청한다(`202`). 이후는 [수정 동의 여부 전송](#수정-동의-여부-전송). 반영 시 수정 이력(작성자·시각·수정 메시지)이 기록되어 타임라인·로그에 쓰인다.
- 입력: `workspace_id`, `file_id`, `content`(수정된 **전체 내용**, diff 아님), `branch`(선택), `commit_message`(선택, 타임라인에 표시), `base_version`(필수, 수정 시작 시 보던 파일 버전).
- 출력: `200 OK` — `file_id`, `version`(반영 후 버전, 다음 수정의 `base_version`) / `202 Accepted` — `request_id`, `approvers[]`(닉네임).
- 예외: `401` 마스터 키 없음 / `403` 소속 아님, **문제 파일 영역 대상**(복사본을 만들어 수정) / `404` / `409` 같은 파일에 대기 중 요청 있음·`base_version`이 최신 아님·비밀번호 미설정 / `423` 잠김.
- 비고: 대기 중인 수정 내용은 **워크스페이스 마스터 키로 암호화해 저장**(평문 보관 금지). 수정 메시지를 포함한 이력 메타데이터는 암호화하지 않는다(종료 후 타임라인이 키 없이 만들어져야 하므로). 알림·응답은 WebSocket.

### 파일 삭제
`참가자 · competition · 로그 페이지, 문제 풀이` — 동의 플로우
- 흐름: "파일 수정"과 같은 동의 플로우. 요청 시점에 그 파일을 연 다른 팀원이 없으면 즉시 삭제, 있으면 전원 동의 또는 팀장 강제 적용이 필요하다.
- 입력: `workspace_id`, `file_id`, `branch`(선택, 기본 `main`).
- 출력: `200 OK` — `data: null` (즉시 또는 동의·강제 적용 완료) / `202 Accepted` — `request_id`, `approvers[]`.
- 예외: `404` / `403`(소속 아님, `404` 가능) / `423` / `409` 같은 파일에 대기 중 요청 있음 / `403` 문제 파일 영역 소속(수정·삭제·이동 불가, 복사만 허용).
- 비고: 명세는 "이력에는 남고 최신 트리에서만 제거"를 제안했다. DB는 hard delete + 로그의 경로 스냅샷으로 같은 목적을 달성한다 → [erd.md](erd.md#원본-대비-변경-사항). 폴더 안 마지막 파일이 삭제되면 폴더는 자동으로 사라진다.

### 파일 이동
`참가자 · competition · 문제 풀이` — 즉시 반영
- 흐름: 파일의 `file_path`(와 필요하면 `area`)를 바꾼다. 이름만 바꾸는 이름 변경도 이 기능이다. **같은 문제 안에서만** 가능하고 팀 풀이 ↔ 라이트업 이동은 허용한다. 서버가 출발지·목적지가 문제 파일 영역이 아닌지, 새 경로가 규칙을 지키는지, 목적지에 같은 경로나 겹치는 폴더가 없는지 검증한다. 이동은 로그에 기록된다.
- 입력: `workspace_id`, `file_id`, `destination_area`(선택, `team_work`|`writeup`, 미지정 시 현재 영역), `destination_path`(필수).
- 출력: `200 OK` — `file_id`(이동해도 불변), `area`, `file_path`.
- 예외: `404` 없는 `workspace_id`·`file_id` / `403` 접근 권한 없음·출발지가 문제 파일 영역·목적지가 문제 파일 영역 / `400` 경로 규칙 위반·잘못된 영역 / `409` 목적지 경로 충돌·폴더 겹침 / `423` 잠김.
- 비고: 내용·파일 ID는 바뀌지 않고 경로(와 영역)만 바뀐다. 폴더 단위 이동은 없다.

### 파일 복사
`참가자 · competition · 문제 풀이` — 즉시 반영
- 흐름: 어느 영역의 파일이든 팀 풀이/라이트업 영역으로 복사한다. 목적지가 문제 파일 영역이면 거부. 복사본은 **새 `file_id`를 갖는 별개 파일**이다. **원본을 원본 키로 복호화한 뒤 워크스페이스 마스터 키로 재암호화**해 저장한다(원본이 문제 파일 영역이면 CTF 키, 그 외는 워크스페이스 키).
- 입력: `workspace_id`, `source_file_id`(필수), `destination_area`(선택, 기본 `team_work`), `destination_path`(선택, 기본 원본과 같은 경로).
- 출력: `201 Created` — `file_id`, `area`, `file_path`.
- 예외: `404` / `403` 접근 권한 없음·목적지가 문제 파일 영역 / `400` 경로 규칙·영역 오류 / `409` 목적지 충돌(원본과 같은 영역·경로 포함) / `401` 마스터 키 없음(재암호화에 필요) / `410` 원본이 문제 파일인데 CTF 키 폐기됨 / `423` 잠김.
- 비고: 제한은 하나뿐 — 문제 파일 영역에는 복사본이 생기지 않는다. 문제 파일 원본은 수정할 수 없으니 복사본에서 작업을 시작하는 용도.

### 파일 메모
`참가자 · collaboration · 문제 풀이` — 즉시 반영
- 흐름: 파일에 팀원과 공유되는 메모를 남긴다. 승인 절차 없음. 소속 검증 후 저장하며 메모는 파일 내용과 별도로 관리한다. **워크스페이스 마스터 키로 암호화**.
- 입력: `workspace_id`, `file_id`, `memo_content`(필수).
- 출력: `200 OK` — `memo_content`, `updated_by`(닉네임), `updated_at`.
- 예외: `401` 마스터 키 없음 / `403`→`404` / `423` 잠김.
- 비고: 메모 조회는 별도 API 없이 "파일 내용 조회"의 `memo` 필드로 내려준다. 파일당 메모 1개.

### 풀이 완료 표시 (자가 체크)
`참가자 · competition · 문제 풀이, 문제 폴더` — 즉시 반영
- 흐름: 팀원 누구나 문제의 풀이 완료를 표시·해제한다(팀 단위 상태). 서버가 로그인·소속·잠금과 문제가 이 워크스페이스에 추가됐는지 확인하고, 표시한 사람과 시각을 남긴다. 표시·해제는 로그와 타임라인에 기록된다. 모니터링의 "푼 팀" 집계 기준이며 **정답 검증은 하지 않는다**.
- 입력: `workspace_id`, `problem_id`, `solved`(boolean, true=표시/false=해제).
- 출력: `200 OK` — `solved`, `updated_by`, `updated_at`.
- 예외: `400` / `401` / `403`→`404` / `404` 없거나 추가되지 않은 문제 / `423` 잠김.
- 비고: 동의 절차 없음. 표시가 엇갈리면 마지막 변경이 우선. 마스터 키가 필요 없는 메타데이터라 암호화하지 않는다.

### 파일/메모 내용 복사
`참가자 · competition · 문제 풀이` — **프론트 전용, 백엔드 API 없음.** 이미 복호화되어 렌더링된 내용을 브라우저 클립보드 API로 복사한다.

### 코드 뷰어 (문법 하이라이팅)

## 브랜치

메인 브랜치 `main`은 워크스페이스 생성 시 자동으로 만들어지며 **삭제할 수 없다**.

### 브랜치 목록 조회
`참가자 · collaboration · 브랜치 탭` — Claude 검토(2026-09-20)에서 추가된 제안 항목.
- 입력: `workspace_id`. 출력: `200 OK` — `branches[]`(`branch_name`, `base_branch`(메인은 없음), `updated_at`, `updated_by`).
- 예외: `401` / `403`→`404` / `404`. 잠긴 워크스페이스에서도 읽기 전용 조회 가능.

### 브랜치 생성
`참가자 · collaboration · 브랜치 탭, 로그 페이지` — 즉시 반영
- 흐름: 현재(또는 지정한) 기준 브랜치로부터 새 브랜치를 만든다. 기준 브랜치의 팀 풀이·라이트업 영역 파일을 복제한다(같은 워크스페이스 키로 암호화된 값이라 복호화 없이 암호문을 그대로 복사, `version`은 1). 문제 파일 영역은 복제하지 않고 메인의 것이 보인다.
- 입력: `workspace_id`, `branch_name`(필수, 워크스페이스 안에서 unique), `base_branch`(선택, 미지정 시 메인).
- 출력: `201 Created` — `branch_name`, `base_branch`.
- 예외: `409` 이름 중복 / `403` 접근할 수 없는 워크스페이스 / `423` 잠김(종료 후 생성 불가).

### 브랜치 삭제
`참가자 · collaboration · 브랜치 탭, 로그 페이지` — 동의 플로우
- 흐름: 요청 시점에 그 브랜치를 연 다른 팀원(보기만 하는 팀원 포함)이 있으면 전원 동의 또는 팀장 강제 적용이 필요하다. 없으면 즉시 삭제.
- 입력: `workspace_id`, `branch_name`.
- 출력: `200 OK` — `data: null` / `202 Accepted` — `request_id`, `approvers[]`.
- 예외: `400` 메인 브랜치 / `404` / `403`(`404` 가능) / `409` 같은 브랜치에 대기 중 삭제 요청 있음 / `423` 잠김(별도의 "브랜치 잠금" 개념은 없음).

### 브랜치 병합
`참가자 · collaboration · 브랜치 탭, 로그 페이지` — **팀장 동의만 필요** (열람 중 팀원 동의 없음)
- 흐름: 참가자가 `source_branch` → `target_branch` 병합을 요청하면 서버가 pending으로 저장하고 **팀장에게만** `merge_request_created`를 실시간 전달한다(팀장이 접속 중이 아니면 접속 시 대기 목록으로 받음). 팀장이 동의하면 병합하고 거부하면 취소된다. 결과는 요청자와 팀장에게 `merge_request_result`로 간다. 충돌이 없으면 자동 병합, 있으면 병합을 거부하고 충돌 파일 목록을 반환한다. **요청자가 팀장이면 요청·동의 없이 바로 병합**한다. 60초 시한이 없고 팀장이 응답하거나 요청자가 취소하거나 워크스페이스가 잠길 때까지 대기한다.
- 입력: `workspace_id`, `source_branch`, `target_branch`(필수, 서로 달라야 함), `message`(선택, 팀장에게 보여줌).
- 출력: `202 Accepted` — `request_id`, `approver`(팀장 닉네임) / `200 OK`(요청자가 팀장) — `target_branch`, `merged_files[]` / 이벤트 `merge_request_result` — `status`(`merged`|`rejected`|`cancelled`|`conflict`), `merged_files[]`, `conflict_files[]`.
- 예외: `400` 같은 브랜치 / `401` / `403` 소속 아님(`404` 가능)·팀장이 아닌데 `merge_response`를 보냄·요청자가 아닌데 `cancel`을 보냄 / `404` / `409` 같은 병합 요청이 이미 대기 중·팀장이 직접 요청했는데 충돌(충돌 파일 목록 함께 반환) / `423` 잠김.
- 비고: 참가자는 승인 없이 병합을 실행할 수 없다. 팀장이 반대하면 요청은 취소되고 요청자는 고쳐서 다시 요청할 수 있다. 팀장 응답은 WebSocket `merge_response`(`request_id`, `consent`), 요청자 취소는 `cancel`. 응답자는 소켓에 연결된 로그인 세션으로 식별하며 요청 본문으로 사용자를 받지 않는다. 병합으로 대상 브랜치의 파일 행이 바뀌면 그 행의 `version`을 +1 하고 새로 생기는 행은 `version = 1`이다. 문제 파일 영역은 병합 대상이 아니다. **충돌 판정 기준은 아직 정해지지 않았다** ([erd.md 미결정 1](erd.md#미결정-사항)).

## 실시간 (WebSocket)

### 실시간 연결 (웹소켓)
`참가자 · collaboration · 문제 풀이, 브랜치 탭`
- 흐름: 워크스페이스에 들어오면 클라이언트가 소켓을 하나 맺고 열람 상태·동의 요청·응답·결과 알림이 모두 이 연결로 오간다.
  - **연결 시 검증**: `SID` 쿠키 인증, **`Origin` 헤더 검사**(허용 출처가 아니면 거부), 워크스페이스 소속, 세션에 워크스페이스 마스터 키 캐시 존재(없으면 거부하고 "워크스페이스 참가"로 유도).
  - **메시지마다** 소속과 잠금 여부를 다시 확인한다(연결 시점에만 확인하지 않음).
  - 서버→클라이언트: `presence_changed`, `change_request_created`(승인자에게, 요청자·수정 메시지·수정 내용 포함), `change_request_progress`, `change_request_result`(반영/취소/무효/강제 적용), `merge_request_created`(팀장에게), `merge_request_result`(병합됨/반대/취소/충돌), `workspace_locked`.
  - 클라이언트→서버: `view_start`/`view_end`, `consent`/`force`/`cancel`, `merge_response`.
  - 끊기면 10초 재연결 유예를 두고 같은 세션이 다시 연결하면 열람 상태를 복구한다. 끊긴 동안의 알림은 재연결 시 대기 중 요청 목록으로 다시 받는다.
  - 로그아웃·세션 만료 시 연결 종료. 잠금 시 해당 CTF 연결을 모두 끊고 새 연결은 거부한다.
  - **마스터 키는 소켓으로 보내지 않는다.** 파일 내용·diff는 서버가 복호화해 검증된 팀원 연결에만 보낸다.
- 입력: `workspace_id`(세션 쿠키와 함께).
- 출력(연결 성공): `pending_requests[]`(내가 요청자 또는 승인자인 대기 중 요청), `presence[]`.
- 예외: 세션 없음·마스터 키 없음 `401` / 허용되지 않은 Origin `403` / 소속 아님 `403`(`404` 가능) / 잠긴 워크스페이스 `423`(읽기 전용 열람은 일반 조회로).
- 비고: 연결 수·메시지 빈도 rate limiting. 서버 다중화 시 Redis pub/sub 등 필요(구현 시 결정).

### 열람 상태 전송 (파일·브랜치)
`참가자 · collaboration · 문제 풀이, 브랜치 탭`
- 흐름: 파일(또는 브랜치 선택 화면)을 열면 `view_start`, 닫거나 이동하면 `view_end`. 탭이 5분 이상 비활성이면 클라이언트가 `view_end`를 보낸다(자리를 비운 사람이 다른 팀원의 수정을 계속 막지 않도록). 서버는 열람 상태를 Redis에 TTL과 함께 저장하고, 연결이 끊기면 10초 유예 뒤 지운다. 같은 유저의 여러 탭은 유저 단위로 합쳐 하나라도 열려 있으면 열람 중으로 본다. "파일 수정/삭제/브랜치 삭제" 때 이 상태로 승인자를 계산(요청자 제외).
- 입력: `type`(`view_start`|`view_end`), `workspace_id`, `target_type`(`file`|`branch`), `target_id`.
- 출력: 성공 시 본문 없음 / 이벤트 `presence_changed` — `viewers[]`(같은 대상을 연 다른 팀원 닉네임).
- 예외: 인증 실패→연결 거부·종료(`401` 상응) / 소속 아님 `403` 상응 / 없는 `target_id` `404` 상응 / 잠김 `423` 상응.
- 비고: 파일 내용은 저장하지 않고 "누가 어떤 대상을 열었는지"만 기록한다. 5분·10초 값은 설정값.

### 수정 동의 여부 전송
`참가자 · collaboration · 문제 풀이` — WebSocket 메시지. HTTP로도 받을지는 구현에서 결정.
- 흐름: 파일 수정·파일 삭제·브랜치 삭제 요청이 접수되면 서버가 **요청 시점에 승인자 목록을 고정**한다(요청자 제외, 이후 열람을 시작한 팀원은 이번 요청의 승인자가 아님). 승인자가 없으면 즉시 반영.
  - 서버는 각 승인자의 연결로 동의 요청(요청자·수정 메시지·수정 내용)을 보내고 요청자에게는 현황을 보낸다.
  - 승인자는 `consent = true|false`. **전원 동의 → 반영(`applied`)**. 반대가 하나라도 나오면 자동 반영되지 않고 남은 시한 동안 대기하며 그 사이 **팀장이 `force = true`로 강제 적용**할 수 있고, 시한이 끝나면 취소(`cancelled`).
  - **요청 후 60초 안에 응답하지 않은 승인자는 반대로 처리**(침묵을 동의로 보지 않음).
  - 요청자는 `cancel = true`로 취소할 수 있다.
  - 승인자가 열람을 종료하거나 10초 재연결 유예를 넘기면 승인자에서 제외한다. 남은 승인자가 없거나 모두 동의했으면 그 시점에 판정한다.
  - 대기 중 같은 대상에 다른 변경이 먼저 반영돼 기준 버전이 달라지면 **자동 무효(`invalidated`)**. 자동 병합은 없고 요청자가 최신 기준으로 다시 요청한다. **같은 파일(브랜치)에 대기 요청은 1개만** 허용한다.
  - 워크스페이스가 잠기면 대기 요청은 모두 취소된다.
  - 결과(반영/취소/무효/강제 적용)는 실시간 전달되고 로그·타임라인에 기록된다. 강제 적용 사실도 남긴다.
  - 동의자는 소켓에 연결된 **로그인 세션으로 식별**한다(요청 본문으로 사용자를 받지 않음).
- 입력: `request_id`(필수), `consent`(조건부), `force`(기본 false), `cancel`(기본 false). **`consent`/`force`/`cancel` 중 정확히 하나만** 보낸다.
- 출력: `200 OK` — `status`(`pending`|`applied`|`cancelled`|`invalidated`), `remaining_approvers`.
- 예외: `400` 셋이 모두 없거나 둘 이상 / `401` 마스터 키 없음 / `403` 소속 아님·승인자 아님·팀장이 아닌데 `force`·요청자가 아닌데 `cancel` / `404` 없는 `request_id` / `409` 이미 종료된 요청이거나 이미 응답함 / `423` 잠김.
- 비고: 동의 여부는 파일 내용과 별도 관리. 대기 중 수정 내용은 워크스페이스 키로 암호화. 60초·10초는 설정값. 메시지마다 소속·잠금 재확인. 종료 후에는 새로 전송할 수 없다.

## 잠금·타임라인

### 워크스페이스 잠금
`참가자 · competition · 문제 풀이, 타임라인 및 요약` — 내부 처리(스케줄러)
- 흐름: **스케줄러가 10분 간격**으로 종료 시각이 지난 워크스페이스를 조회해 `workspace_status`를 `open → locked`로 바꾼다. 잠금과 함께 ① 해당 CTF 워크스페이스의 **마스터 키 캐시를 Redis에서 폐기**(로그인 세션은 유지, 이후 열람은 비밀번호를 다시 입력해 읽기 전용), ② 대기 중인 수정·병합 요청을 모두 취소, ③ `workspace_locked` 이벤트를 보낸 뒤 WebSocket 연결을 모두 끊고 새 연결 거부, ④ 로그에 잠금 이벤트(`user_id = NULL`)를 기록. 타임라인은 저장하지 않고 조회 시 계산하므로 잠금 시 집계 작업은 없다. 같은 스케줄러가 `end_at + access_days_after_end`가 지난 CTF의 **문제파일 마스터 키를 폐기**한다.
- 입력: `now`, 각 워크스페이스의 `end_at`·`workspace_status`. 출력: 내부 처리(`workspace_status = locked`).
- 예외: 대상이 없으면 에러 없이 아무 동작 없이 주기를 종료.
- 비고: 스케줄러 10분 공백은 "종료 후 수정 불가"의 lazy check가 메운다. `end_at` 연장으로 종료 시각이 다시 미래가 되면 `locked → open`으로 되돌린다. 타임라인·총 요약은 다시 `409`(진행 중)가 되고 재종료 후 새로 계산된다. 잠금은 화면 전환 조건이 아니다(워크스페이스·타임라인 페이지는 별개로 항상 공존, 자동 전환 없음).

### 종료 후 수정 불가
`참가자 · summary · 문제 풀이, 타임라인 및 요약` — 모든 쓰기 기능 공통 검사(lazy check)
- 흐름: **모든 쓰기 요청은 처리 전에 잠금 여부를 먼저 검사**한다. `workspace_status = locked`이거나 `now > end_at`이면 종료된 것으로 본다.
- 출력: `423 Locked` — 모든 쓰기 기능 공통 에러 코드. 소속 검증 실패(`403`/`404`), 문제 파일 영역 조작 금지(`403`)와 구분하기 위해 `423`으로 통일한다.
- 비고: **쓰기만 막는다.** 잠긴 워크스페이스의 조회(파일 내용, 타임라인 등)는 읽기 전용으로 허용. 대상 쓰기: 파일·브랜치·메모·풀 문제 추가·동의 여부 전송·풀이 완료 표시 등이며 **WebSocket 메시지도 매번 같은 검사를 한다.** `end_at` 연장으로 다시 미래가 되면 `open`으로 돌아간다.

### 타임라인 집계
`참가자 · summary · 타임라인 및 요약` — 내부 처리 (API 아님)
- 흐름: 워크스페이스의 수정 이력(작성자·시각·수정 메시지·변경 파일 경로)을 시간순으로 모아 타임라인 데이터로 가공한다. **저장하지 않고 조회 시 `log`에서 계산**하며, **잠긴 워크스페이스에 대해서만** 계산한다(종료 후 확정본만 제공). 항목 구성: 파일 이벤트는 `changed_files = [target_file_path]`, 병합·풀이 완료·요청 결과 같은 파일 외 이벤트는 `[]`.
- 입력: `workspace_id`. 출력(내부 저장용): `timeline[]`(`timestamp`, `author`, `message`, `changed_files[]`).
- 예외: `409` 아직 잠기지 않은(대회 진행 중) 워크스페이스에 대한 집계 요청.
- 비고: "완성된 라이트업 자동 생성"이 아니라 "라이트업 작성용 힌트·타임라인". `end_at` 연장으로 다시 열리면 `409`가 되고 재종료 후 다시 계산된다. 타임라인에는 수정 이력과 함께 **수정 요청의 결과(반영/취소/무효), 팀장 강제 적용 표시, 브랜치 병합 이력, 풀이 완료 표시 변경**도 포함한다. 집계는 마스터 키 캐시가 폐기된 상태에서 수행되므로 **평문 메타데이터(작성자·시각·수정 메시지·변경 파일 경로)만** 사용한다.

### 타임라인 출력
`참가자 · summary · 타임라인 및 요약`
- 흐름: 종료(잠금)된 자기 워크스페이스의 확정 타임라인을 조회한다. 워크스페이스와 타임라인은 별개 페이지로 항상 공존하며 자동 전환이 없다. 대회 진행 중 타임라인 페이지에는 "종료 후 제공" 안내만 표시한다. UI는 가운데 세로선을 기준으로 로그가 좌우 번갈아 붙는 방식(README).
- 입력: `workspace_id`(필수).
- 출력: `200 OK` — `timeline[]`(`timestamp`, `author`, `message`, `changed_files[]`).
- 예외: `409` 아직 확정되지 않음(진행 중) / `404` 없는 워크스페이스 / `403` 소속 아님(`404` 가능).
- 비고: 평문 메타데이터(`log`)만 쓰므로 **마스터 키(비밀번호 재입력) 없이 소속 검증만으로** 조회할 수 있다.

| 6 | 브랜치가 있을 때 문제 파일이 어느 브랜치에 있는지 명세에 없다 | 문제 파일은 메인 브랜치에만 두고 모든 브랜치에서 보임. 브랜치 생성은 팀 풀이·라이트업 파일만 복제 | 풀 문제 추가, 파일 트리 조회, 브랜치 생성 |
| 7 | `204 No Content`가 README의 "`data`는 항상 포함"과 충돌 | `204`를 쓰지 않고 `200`/`201` + `data: null` | 읽는 법, 로그아웃, 파일 삭제, 브랜치 삭제, 문제 관리 |
